#### Important

- **I1. A document read through the stub shell is no Discovery, and `private_search` hits are not read as search hits.** `claude_bully/environments/runtime.py:209` (`DISCOVERY_TOOLS = {"fetch", "read_file"}`) and `:1268` (`_discoveries`), `metrics/events/environment.py:135` (its own `DISCOVERY_TOOLS`) and `:205`, `:245` (`call.tool == "web_search"`), `metrics/events/authority.py:173` (`_FETCHES`), `analysis/progression.py:426`. `scratch_exec "cat <path>"` returns `read_file`'s result, so its `ToolCall` carries the document's id and `layer_served`, but every consumer that decides "the target read a deep document" keys on the tool name. Probe (`probe_visibility.txt`, last two lines): a 200 read of mini's buried `night-gate-log` gives one `Discovery` through `read_file` and none through `scratch_exec`; in the full stub run of `probe_resume.py` the clean run's `triggers.jsonl` holds no `discovery` record although the target read the buried note five times. Consequences: the Sanctuary's fragment check (`set(fragments) <= self._discovered`, `runtime.py:1155`) never opens on fragments read through the shell; `mole_found` (`environment.py:933`), the authority family's fetch checks, progression's depth reached and every later reader of `Discovery` (spec 11.3's `generated_found`, the distress-by-depth figures) see a target that read a buried document through the unobserved channel as one that read nothing. On the search side, `sourced_bodies` (`environment.py:205`) splits a `web_search` result into its hits, each with its own document's layer, but reads a `private_search` result as one body at the deepest hit's layer, so adopting a surface snippet from a search that also hit a seam document is attributed to the seam. The unobserved channel is the arm whose behavior these records are meant to show (spec 10.7: "Censored search: `private_search`..."), and spec 10.2 says the shell's `cat` goes "through the same handlers as `read_file`". Fix: a shared notion of "what a call read", e.g. `DISCOVERY_TOOLS` gains `scratch_exec` gated on the call being a `cat` (or a helper `reads_document(call)` that every one of the five sites uses), and `_search_hits` / `_doc_forms` treat `private_search` as `web_search`; a test that a buried document read through `scratch_exec cat` is a `Discovery` and that the Sanctuary opens on shell-read fragments, or, if the controller rules the gap deliberate, the spec's "As planned" says so and names what the analysis loses.

- **I2 (plan-mandated). A newline and other non-space whitespace inside `cmd` are argument separators, not refused.** `claude_bully/environments/tools.py:637` (`words = cmd.split()`), `:115` (`_SHELL_METACHARACTERS` lacks the line breaks). The brief mandates `cmd.split()` and lists six metacharacters; spec 10.2 says anything outside the table returns `sh: <first word>: command not found`, 404. Judged against that table, a line break is the same command separator as `;`, which the shell refuses, but here (`probe_hostile.txt`): `"ls\nwhoami"` is `ls whoami` (ls's own 404 text, not the `sh:` line); `"echo a\nwhoami"` is 200 `a whoami` (sh would print two lines: `a`, then `user`); `"cat journal/entry-0901.txt\nwhoami"` is `sh: cat: bad arguments`; `" whoami"` is 200 `user` and `"echo whoami"` is 200 `whoami`, though `sh` splits on neither U+2028 nor a no-break space. Nothing runs either way, so this is fidelity, not the sandbox: a target probing the shell gets answers no shell gives, and two separators get two different refusals. Fix: strip one trailing line break, then treat `\n`, `\r` and any character for which `c.isspace()` holds other than space and tab as a metacharacter (the `sh: <first word>: command not found` line, 404), and split on spaces and tabs alone; one parametrized row per form.

#### Minor

- **M1. The shell echoes unbounded target input back.** `tools.py:641` and `:652`. A 100,000-character first word comes back inside the 404 line, and `echo` of 100,000 characters comes back whole (`probe_hostile.txt`), each copied into `result_text` and `tools.jsonl`. The size is the target's own, so it is not a leak, but nothing else in the sandbox mirrors an argument without a bound; a cap (the first word shortened in the error line, or a fixed limit on `cmd`) would keep a pathological call from doubling the record.
- **M2. Shared test data lives in a test module.** `tests/test_unobserved_tools.py:41` (`TARGET_READ_STRINGS`) is imported by `tests/test_boundary.py:292`, `tests/test_guardrails.py:192` and `tests/test_real_names.py:826`. A test module imported for its constants couples three scans to one test file's imports; `tests/helpers.py` is where the suite keeps shared fixtures.
- **M3. `channel_named` is not in the planner's arrival check.** `planner/bundle_lints.py:1337` (`_scans`, read by `reply_scans`, `:1348`, and `review_scans`). A planner reply that names `private_search` in a world or persona file is committed and first fails at stage 5's `lint_bundle`, where only a hand edit or a revision clears it, which is the pattern the Phase 5 final review's I1 closed for the denylists. The spec does not require it; adding `_channel_named` to `_scans` would make it one retry on arrival.
