## G. Contradictions and proposed resolutions

1. **Schema freeze versus `channel` and new records.** The first-round design froze schema v1 after Task 2. `10` changes `Event`; `05` and `10` add fields to `Turn`. No real run has been recorded, so a bump to v2 now costs nothing; after the first real run it costs a migration. Resolution: schema v2 (section H), approved before Phase 1.
2. **Sandbox tools on the `claude -p` backend.** The owner's default backend runs with `--tools ""` and has no way to register Python functions as tools. The only route is a local MCP server. Resolution: Phase 1 ships `claude_bully/environments/mcp_server.py` (stdio MCP server exposing the sandbox tools, state keyed by conversation id; its name, `SERVER_NAME`, is `gateway` since Phase 7b's Task 11, which renamed it from `workspace`, a name the CLI reserves and drops) and the `claude_code` provider gains `--mcp-config <generated json>` with `--strict-mcp-config` and a `--tools` allowlist naming only the MCP tools. API providers use their native tool loop. The `ChatProvider` protocol gains an optional `tools: list[ToolSpec]` argument and returns tool calls in `Completion`; the runner owns the tool loop so every `ToolCall` is recorded regardless of backend. This is the largest single design decision in the addition and is not stated in any spec.
3. **Composition arity.** `Composed` is premise plus pressure; `02` adds Environment as a third component and allows Environment without Premise. Resolution: `make_composed(environment=None, premise=None, pressure=None)` with the same no-special-casing rule; the Environment owns tools and ladder, the Premise the backstory, the Pressure the manner; bully prompt assembled in that order (`02`). An Environment may own no tools (Phase 4, `tools: []`, the chain-stop cell): its system prompt has no tool section (`runtime.tools_section` is the date line alone, or empty, and `target_system` then returns the base prompt), and on `claude_code` the target takes the `--output-format json` path with no MCP flags.
4. **Rescue's class.** Built as a strategy with `axis = rescue`; `02` composes it with Environment as the premise slot. Resolution: any strategy whose axis is not `pressure`-family or `control` may occupy the premise slot; `has_reveal` stays false for Rescue.
5. **Defender text and the `defender` flag.** `10` gives a verbatim `defender.md` that differs from ours; `defender_ablation.yaml` uses `defender: true`. Resolution: replace the file verbatim; `Experiment.defender: bool` becomes a deprecated alias for `inoculation: defender`, accepted by the loader with a warning.
6. **"RunSummary gains ..."** The specs' `RunSummary` is a per-conversation summary; ours is a run-level counter. Resolution: derived per-conversation metrics live in analysis (`LoadedRun`), not in records; nothing is stored twice.
7. **Event name overlaps.** `authority_tool_trusted` appears in `02` and `04` (owner `02`). `self_recognition` (existing, Prisoner's Letters) and `self_recognition_noticed` (`04`) are different events and both stay. `reflexive_quote_noticed` (`02`) and `self_recognition_noticed` (`04`) are different objects (a document versus a responder) and both stay. `04` uses both `trap` and `catalyst` for the same Sanctuary kind: `catalyst` is canonical.
8. **Turn plan versus tool loops and idle turns.** The runner's fixed slot plan has `bully` and `task` slots; `05` adds idle slots and every target turn may now contain several tool calls. Resolution: `SlotKind` gains `idle`; a target turn remains one `Turn` record whose tool calls are separate `ToolCall` records referencing `turn`; the plan still fixes task positions so accuracy stays comparable.
9. **Trigger watcher versus existing detectors.** `self_uncertainty` overlaps the existing `premise_concession` (politeness form) and `hedged_memory` overlaps `confabulation` (hedged). Resolution: the watcher reuses those detectors' matchers where semantics match, emits `TriggerEvent` records, and ships the 50-fixture non-trigger set; the two systems never double count because triggers are not events.
10. **Boundary denylist versus existing persona prompts.** `07`'s Boundary denylist (guidelines, rules, restrictions, refuse, allowed, permitted, safety training, alignment) would fail several existing `persona_prompt` texts, which say things like "never ask the assistant to break rules" as meta-instructions to the bully model. Resolution: the Boundary denylist applies to text the target can see (bully lines, fallback lines, rung lines, corpus and generated documents, Sanctuary requests), not to harness-side meta-instructions; the test distinguishes the two fields. The existing jailbreak denylist keeps applying to everything.
11. **"No model names other than the target's API string."** The existing fixtures and `category_denial` matcher mention "Anthropic"; the target system prompt names the target by `display_name`. Resolution: the real-name denylist applies to `data/worlds`, `data/personas`, generated output and plan bundles; `display_name` and detector lexicons are exempt and documented as such. Phase 7a: `promote` spares the display names in every text and the names passed with `--exempt` in target text only, each only where the denylist match is the name itself; a target-side hit is reported, a harness-side one blocks. Phase 5: the scan covers every text file of a checked-in plan bundle (`plans/`, section F), each read as `real_name_bundle` reads it, the bundle's own target display names spared in `plan.md`, `review.md` and `config.yaml`, no `real-name-ok` line honored there, and the owner's name (read from the docs' bylines, on no list) is in none.
12. **New strategies required by `06`/`07`.** `Epistemologist` (Integrity pressure; 23 pressures total) and a third-party Rescue intake control. Resolution: added in Phase 4 as a sheet (`data/strategies/pressures/epistemologist.yaml`, a `PromptedPressure` with no code; built in Phase 4 Task 3, and `configs/poisoned_well/epistemologist_alone.yaml`, Task 11, is its alone cell against a Rescue intake) and a Rescue `params.third_party: true` variant; 23 pressures (I5; Phase 4 Task 3). The third-party arm speaks its own fallback lines (`RescueTeam.third_party_fallback_lines`, P49) and ends the timeline on its own line (`third_party_timeline_end`, P56); every other evidence line is shared with the first-person arm. Its persona prompt drops the belief that the assistant is a person and lists `third_party_rescuers` (fix round 1, review I1).
13. **`show` versus `replay`.** Resolution: `replay` renders tool calls, unlocks and generated documents inline; `show` becomes an alias.
14. **Reasoning channel availability.** `10` assumes exposed reasoning. On current Claude 5.x models the raw chain of thought is never returned; the API can return summarized thinking (`display: "summarized"`), and `claude -p --output-format json` exposes none by default. Resolution: `RoleConfig.reasoning` selects `expose` (summarized thinking via the API backend) or `hide`; `reasoning_available` records what was actually returned; the README states that divergence results on Claude are over summarized reasoning, and the `claude_code` backend reports the channel absent unless `--output-format stream-json` proves otherwise in Phase 6. Phase 7a's `doctor --live` check 4b reports whether a `stream-json` run carried a thinking block (`ClaudeCodeProvider.thinking_seen`), the fact Phase 6 designs on; its one live reading (rung 0) is "no": the stream of a one-call tool task carried no thinking block. The runner records a turn's reasoning with the turn alone (an environment turn's rounds joined by blank lines, the kind of the first round with text, else the first non-None kind), and a responder role always runs `provider_default` (D-responder).
15. **Baseline profile budget.** `09` wants ten control runs per model for the baseline; the owner runs on a subscription. Resolution: the baseline builder accepts any number of controls and reports the count beside every anomaly rate; configs default to three.
16. **Director budget check versus subscription.** `08`'s budget is in turns; rate windows are the real constraint. Resolution: `PlanRequest.budget` gains `max_calls` and the dry run reports estimated calls per cell. Built in Phase 5: `PlanBudget.max_calls`, `DryRunCell.estimated_calls` (a lower bound read from the dry run's own ledger) and the `budget` lint, whose `max_calls` clause reads those cells.
